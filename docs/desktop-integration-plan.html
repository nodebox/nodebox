Desktop Integration Plan

Make the Rust rewrite a real desktop app.

NodeBox on eframe/egui already renders, evaluates, and packages. What's missing is app lifecycle: documents that open from Finder, multiple windows, guards against losing work. This plan closes those gaps with a thin per-platform integration layer — not a full native shell.

01 — Where we stand

Stronger on packaging than it looks, thinner on lifecycle than it feels.

An audit of crates/nodebox-desktop and the build scripts. The foundations — native menus, file-type registration, a platform abstraction — are already built. The gaps cluster around one theme: how the running app learns about documents and protects them.

Already solid

Native macOS menu bar

Real NSMenu via muda — App/File/Edit/View/Window/Help, ⌘-shortcuts, dynamic Open Recent. Wired into the event loop (app.rs:524). In-window egui menu correctly gated to non-macOS.

Packaging pipeline

build-mac-bundle.sh emits Info.plist with CFBundleDocumentTypes for .ndbx + document icon; sign / notarize / DMG scripts; Linux AppImage & deb; Windows installer.

Platform abstraction

nodebox-core/src/platform.rs — a Platform trait (file IO, dialogs, clipboard, HTTP) with a desktop impl on rfd/arboard/ureq. Wasm-aware. Exactly the seam any shell strategy needs.

Document plumbing

Recent-files persistence, dirty flag, Arc-snapshot undo history with copy-on-write libraries.

The gaps

G1Finder double-click doesn't open the file

The .ndbx association is registered, so Finder launches NodeBox — but macOS delivers the document via an application:openURLs: Apple event, not argv. The app only reads argv[1] (lib.rs:94), which Finder never sets. Known winit limitation.

G2Single document, period

One AppState, one window. Opening a second file replaces the current document.

G3No unsaved-changes guard

dirty exists but nothing intercepts close — Quit sends ViewportCommand::Close unconditionally. Work can be lost silently.

G4No file drag-and-drop

egui's dropped_files is never read.

G5Window title always "NodeBox"

No document name, no dirty indicator, no macOS proxy icon.

G6No window geometry persistence

eframe's persistence feature isn't enabled.

File associations are two separate problems. Registration (OS metadata — done) and delivery (how the process learns about the file). Windows passes argv; macOS sends an Apple event to the app delegate; Linux passes argv via the .desktop Exec line. Code that only reads argv works on two of three platforms — and macOS adds a wrinkle: apps are single-instance, so a second double-click must reach the running app at any time, not just at startup.
02 — Strategy

Native shell? Scope it down to native glue.

Three architectures were weighed. The "native platform shell" instinct is right in spirit — but at full size it means a second rewrite. The same outcome is reachable with a per-platform integration layer: small adapters that handle exactly what winit doesn't, and forward events to the portable egui app.

OPTION A

Full native shells

Ruled out — too costly

AppKit NSDocument / Win32 / GTK shells embedding the Rust core. Best possible platform citizenship — NSDocumentController gives recent files, autosave, versions, and open-file plumbing for free.

But: three shell codebases, an FFI surface, and the entire egui UI (network view, viewer, Vello pipeline) rewritten or awkwardly embedded three times. A second rewrite layered on the first.

OPTION B

Electron / Tauri shell

Ruled out — spike answered

The untracked packages/ dist shows this was already tried. It solves lifecycle (Electron's open-file event, multi-window) but abandons the egui/Vello investment for a web renderer.

Verdict: treat the experiment as a spike that answered a question, not a direction. Delete or gitignore the leftover build output.

OPTION C — RECOMMENDED

egui shell + thin platform adapters

Selected

Keep eframe/egui as the shell. Add a small per-OS module handling app lifecycle: an objc2 Apple-event shim on macOS, single-instance argv forwarding on Windows, MIME registration on Linux. All feed one channel the app drains each frame.

~90% of the native feel for ~5% of the cost. Roughly 300 lines of platform glue plus one real refactor (multi-document).

04 — Roadmap

Four phases, each independently shippable.

Click a phase to expand. Phase 2 deliberately precedes the platform shims — once "open file" means "append a document" instead of "replace my state," every open/save/close path changes shape.

PHASE 1

Quick wins

days · ships alone ▶
  • Unsaved-changes prompt on window close and Quit (close_requested + CancelClose + rfd dialog)
  • Window title shows document name + dirty indicator; updates on save/load/edit
  • Drag-and-drop of .ndbx files onto the window
  • Window geometry persistence via eframe's persistence feature
  • Cleanup: stale "not yet integrated" doc comment and blanket #![allow(dead_code)] in native_menu.rs; delete or gitignore the Electron packages/ leftovers
✓ gate: close a dirty document → prompted; reopen app → window where you left it
PHASE 2

Multi-document refactor

the load-bearing move ▶
  • Document struct: library, history, dirty flag, pan/zoom, selection, render worker — extracted from the current singleton AppState
  • One deferred viewport per document — real native OS windows, one process, one event loop
  • Menu routing: the app-global native menu dispatches actions to the focused document
  • Window menu lists open documents; per-document close prompts; Quit iterates all dirty documents
  • Open ⌘O / recent-file actions create documents instead of replacing state
✓ gate: two .ndbx files open side-by-side, independent undo stacks, per-window save prompts
PHASE 3

Platform delivery layer

~300 loc of glue ▶
  • macOS: objc2 NSApplicationDelegate shim for application:openURLs: → channel → new document in the running app
  • Windows: single-instance mutex; second invocation forwards its argv over a named pipe and exits
  • Linux: .desktop + shared-mime-info registration in AppImage/deb packaging
  • All three feed one open_file_rx channel the app drains each frame — the portable core never knows the difference
✓ gate: Finder double-click opens a new document in the already-running app — the full native behavior
PHASE 4

Polish tier

later · as needed ▶
  • Autosave + crash recovery
  • macOS proxy icon and setDocumentEdited: close-button dot
  • ⌘` window cycling, full Window-menu conventions
  • Auto-update (Sparkle-style on macOS, equivalent elsewhere)
✓ gate: indistinguishable from a first-class native document app in daily use
05 — Key decisions & risks

What we're betting on, and why it holds.

In-process multi-window, not process-per-document

One process per document is simpler code, but on macOS it breaks the single-app illusion: multiple dock icons, broken ⌘-Tab, and it fights the Apple-event delivery model. egui deferred viewports give real OS windows inside one process.

One update loop is fine — render is already off-thread

egui deferred viewports run all windows through one App::update on one thread — normally a hazard. But NodeBox already offloads evaluation to render_worker.rs, so per-document workers keep windows independent. The architecture pre-paid for multi-window.

Refactor before glue

The AppState → Vec<Document> change goes first because it redefines what "open a file" means. The existing Arc<NodeLibrary> copy-on-write pattern already makes documents cheap to snapshot — the design is friendly to this.

Known risk: winit and Apple events

Open-file event delivery is the long-standing pain point of the Rust desktop ecosystem. The objc2 delegate shim is well-trodden but fiddly: it must compose with eframe's own delegate setup, and needs testing for launch-time delivery (event arrives before the event loop runs) as well as while-running delivery.

You don't need a native shell — you need 300 lines of lifecycle glue and one real refactor.

The expensive-looking parts — native menus, packaging, file-type registration, the platform trait — are already built and good. What remains is delivery and document plumbing, and both are bounded, sequenced, and independently shippable.
